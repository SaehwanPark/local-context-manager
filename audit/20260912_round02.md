I audited the current `main` after merged PR #18, the original `audit/report_20260912.md`, the added regression tests, and the relevant Pi v0.84.4 compaction implementation. The current `main` is exactly PR #18's merge; there are no later code changes muddying the comparison.

## Overall verdict

The original failure-mode report was **legitimate and technically strong**. I do not see any finding among the 13 that I would retract. Importantly, the report distinguished reproduced defects from speculative candidates and explicitly documented things it tried and ruled out.

PR #18 is also a good remediation PR. I would classify the original 13 approximately as **10 fixed, 2 mostly fixed with residual edge cases, and #3 only partially fixed**. The PR head passed the macOS, Ubuntu, and newly added Windows CI matrix.

However, for your stronger criterion—

> don't make local-model context/compaction problems worse, and preferably make them better

—I would **not quite sign off yet**. I found two previously undetected compaction-specific issues that matter more to Qwen-class local deployments than most of the original low-severity findings.

## The most important newly detected issue: LCM can make compaction prefill *harder*

This is the one I would address before calling the extension robust for local models.

Pi v0.84.4 normally keeps **20,000 recent tokens** when compacting.  LCM instead uses 8k / 10k / 12k for aggressive / balanced / relaxed. Balanced proactively triggers at 32k and keeps 10k.

The `session_before_compact` hook does not merely influence *when* Pi compacts. It recomputes the compaction slice with LCM's smaller `keepRecentTokens` and then invokes Pi's lower-level summarizer itself.

That has a counterintuitive consequence. Around a 32k balanced trigger:

| Strategy     | Approx. suffix retained | Approx. history sent for summarization |
| ------------ | ----------------------: | -------------------------------------: |
| Pi native    |                     20k |                                   ~12k |
| LCM balanced |                     10k |                                   ~22k |

Those figures aren't exact because Pi cuts at message boundaries and truncates serialized tool results, but the direction is unambiguous. Pi's summarization request contains the messages being discarded, so **keeping less means asking the local model to prefill more during the compaction itself**.  Tool results get truncated to 2,000 characters during summary serialization, which helps, but user text, assistant text, reasoning, etc. remain relevant.

For a cloud model this is mostly efficiency. For a memory-constrained local model it can be the difference between successful compaction and a prefill-memory rejection.

More importantly, the hook applies to **Pi's overflow-recovery compaction too**, because `buildCustomCompaction()` does not exempt `event.reason === "overflow"`. Pi normally invokes `session_before_compact` during both threshold and overflow recovery.  So after the local model has *already* demonstrated context pressure, LCM can first try the larger/deeper summarization request.

There is good news: this is fail-soft rather than catastrophic. If LCM's custom compaction fails, it catches the error and returns `undefined`, after which Pi performs its native compaction.  But that means a capacity-constrained local server gets a difficult request that may OOM/reject, followed by the easier request it arguably should have received first.

There is another subtle difference: Pi's native summarization uses its configured transient-error retry policy; LCM's direct lower-level `pi.compact(...)` call does not supply Pi's retry policy/callbacks.   Again, fallback eventually restores native behavior, but only after the unnecessary first failure.

**I would change the philosophy here:** LCM should primarily control **when compaction happens**, not make the first compaction **deeper** than Pi's native one. Especially for `reason === "overflow"`, I would return `undefined` unconditionally and let Pi own recovery. For proactive threshold compaction, triggering Pi at 24k/32k/48k while retaining Pi's native 20k is exactly the kind of "make things better without making them riskier" behavior you want.

Deep compaction can remain an explicit semantic/phase-boundary operation, or become a second-stage optimization once a cheap native compaction has already succeeded.

## Second important new issue: the compaction gate can effectively retire itself

The current hysteresis logic rearms only after observed context falls below `rearmTokens`. Balanced therefore rearms at 24k; aggressive at 16k.

The test suite actually locks this behavior in: after a successful `complete(31_000)`, a threshold request remains disabled until an observation reaches 24k.

That works if every compaction shrinks the active context substantially below the rearm point. It fails when, for example:

* balanced profile compacts at ~32k;
* result is 26–30k because of a large recent turn, large summary, images, or other retained material;
* context subsequently grows 30k → 35k → 50k → 80k.

The gate never sees ≤24k, so it never rearms. The context is monotonically growing, making recovery impossible by observation alone.

Pi's own emergency/native threshold can eventually save the session, but for a 128k model Pi's default reserve-based trigger is far later. That means LCM can silently stop providing the proactive protection it exists to provide.

I would treat this as **P1 for local-model reliability**.

The gate should be based on a new **post-compaction epoch**, not require an absolute drop below a fixed watermark. For example, after successful compaction, remember `postTokens`; permit another proactive compaction after the turn cooldown once there has been meaningful new growth or once context crosses the compact threshold again. You still want hysteresis against immediate compaction loops, but "must someday fall below 24k" is too strong an invariant.

## Recovery pointer lifetime is still not fully fixed

PR #18 substantially improved #3: recovery copies now have an explicit lifetime notice, actual references promote LRU position, pruned paths are remembered, failed reads can explain that the copy expired, and stale temp directories get swept.

But the report explicitly called for decoupling recovery-file lifetime from `session_shutdown`.  Current code still runs `cleanupRecoveryStorage()` unconditionally on `session_shutdown`.

And Pi explicitly emits `session_shutdown` not just at process exit but on **new session, resume, fork, reload, and replacement**.

So:

`tool result → reduced output → Full output saved to X → fork/resume/session switch → X deleted`

is still a real lifecycle.

Worse, `cleanup()` does not classify those deleted paths as pruned, so a resumed transcript cannot even benefit from the new "LCM intentionally pruned this" explanation.

For long-running development agents, I would consider this **still part of the original High finding**, not merely cleanup polish.

The better model is session-addressable or TTL-addressable recovery storage. A session file should be resumable while its referenced recovery objects are within their advertised retention period. The new three-day stale sweep gives you most of the machinery necessary; immediate shutdown deletion is working against it.

## Smaller residual issues

There are a few lower-priority gaps worth fixing during the same hardening pass.

Fabric timeout now protects LCM, but `withTimeout()` only stops waiting; it does not abort the provider's operation. A malicious/broken provider can therefore accumulate background promises/work.  This is no longer a root-session wedge, so the main #6 defect is fixed.

Replacement safety checks a mismatching `rootSessionId`, but only when a `rootSessionId` was supplied. A snapshot saying `sessionReplacementSafe: true` with no root ID passes.  For the destructive reset path, I would require presence **and** equality whenever the caller supplied a session ID.

The checkpoint hard-link fallback correctly preserves no-clobber semantics, but the fallback creates the final file with `wx` and then writes its contents directly. A process crash during that write can therefore leave a partial final checkpoint.  That's not the original #12 failure and isn't a major concern, but "atomic checkpoint fallback" would overstate the current guarantee.

Recovery storage also leaves at least one managed file even when that single file alone exceeds `maxBytes` because pruning stops at `managedFiles.length > 1`. In practice Pi's built-in tools already truncate around 50 KB and expose their own full-output path, so this is mainly relevant to third-party/custom tools rather than normal bash/read usage.

## What I would change before the next release

My priority order would be:

1. **Do not deepen Pi's overflow compaction.** `event.reason === "overflow"` should use native Pi preparation, full stop. Prefer native preparation for ordinary proactive compaction too.
2. **Fix `CompactionGate` rearming** so a successful compaction that lands above 24k/16k does not permanently disable proactive protection.
3. **Preserve recovery copies across resume/fork/reload**, using session identity + TTL rather than deleting everything on `session_shutdown`.
4. Make custom/deep compaction an optimization for semantic phase boundaries rather than the universal `session_before_compact` policy.
5. Tighten `rootSessionId` presence and timeout cancellation.
6. Add local-model failure-injection tests around these exact paths.

For #6, the most useful regression suite is not another generic unit-test batch. Simulate a 128k local model and explicitly inject: prefill/OOM failure on the first compaction attempt; transport termination during summary generation; successful compaction returning 26k/30k/33k; Pi `reason: "overflow"`; fork/resume followed by reading an old recovery pointer; and a long agent run where context grows while the root isn't idle. Those tests would directly enforce the guarantee you're actually after.

### Bottom line

**PR #18 is a substantial improvement and the original audit was sound.** The output-reduction, interop, checkpoint, Windows, and configuration portions now look considerably more trustworthy.

But I think your reported experience with local-Qwen compaction exposed a layer the audit did not examine closely enough: **the extension's relationship with Pi's own compaction algorithm**. The current smaller-`keepRecentTokens` override can increase the prefill burden of the compaction request, including during Pi's overflow recovery, and the current gate can stop proactively helping after a not-small-enough successful compaction. Those two issues are precisely contrary to the desired invariant of "don't make things worse; when possible, make them better."

I would therefore call current `main` **good but not yet fully hardened for long-running local-AI workloads**. Fixing those two compaction behaviors plus the recovery-session lifetime issue would change my assessment considerably—at that point the architecture would align very closely with the conservative intervention model you want.
